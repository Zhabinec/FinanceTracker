# Finance Tracker

## 1. Назначение проекта

Finance Tracker представляет собой учебное full-stack приложение для
управления личными финансами.

Пользователь сможет:

- создавать учётную запись;
- регистрировать доходы и расходы;
- распределять операции по категориям;
- просматривать статистику;
- видеть, завершён ли выбранный период в плюс или в минус;
- анализировать структуру поступлений и расходов по категориям.

Это не просто демонстрационный CRUD. Проект должен постепенно показать
решение реальных backend-задач:

- проектирование бизнес-модели;
- хранение и целостность данных;
- аутентификация и авторизация;
- обработка ошибок;
- валидация;
- фильтрация и пагинация;
- транзакции;
- конкурентные изменения;
- тестирование;
- логирование;
- контейнеризация;
- взаимодействие backend и frontend.

## 2. Причина создания

Разработчик проекта имеет коммерческий опыт разработки на C# в Unity,
но хочет перейти в продуктовую backend-разработку на .NET.

Основная цель проекта:

- восстановить знания ASP.NET Core и PostgreSQL;
- изучить современную backend-разработку на .NET 10;
- вспомнить архитектурные решения и научиться объяснять их;
- получить практику разработки полного продукта;
- подготовить качественный проект для GitHub и резюме;
- подготовиться к собеседованиям на позиции C#/.NET Backend Developer.

Разработчику не требуется повторно изучать базовый синтаксис C#.
Основной фокус должен быть на backend-мышлении, данных, HTTP,
архитектуре, надёжности и бизнес-ограничениях.

## 3. Роль Codex

Codex разрешено использовать для генерации production-кода,
конфигурации, тестов, миграций и документации.

Codex не должен искусственно заставлять разработчика вручную писать
однотипный boilerplate-код ради обучения.

При этом Codex не должен без объяснения принимать важные
архитектурные решения.

Перед нетривиальной реализацией Codex должен:

1. Изучить существующий код и документацию.
2. Сформулировать задачу своими словами.
3. Определить бизнес-правила и возможные ошибки.
4. Предложить короткий план.
5. Объяснить важные архитектурные решения.
6. Указать альтернативы, если они действительно имеют значение.
7. Только после этого переходить к реализации.

После реализации Codex должен:

1. Показать, какие файлы были изменены.
2. Объяснить путь запроса через систему.
3. Объяснить, почему код расположен именно в этих слоях.
4. Указать потенциальные риски.
5. Запустить сборку и тесты.
6. Сообщить фактические результаты проверки.
7. Задать разработчику несколько вопросов по сделанному решению,
   если задача содержит важный учебный материал.

Codex должен помогать разработчику понимать систему, но не должен
намеренно замедлять разработку.

## 4. Продуктовая модель

### User

Зарегистрированный пользователь системы.

Основные данные:

- идентификатор;
- email;
- password hash;
- дата регистрации;
- базовая валюта.

Один пользователь не должен иметь доступ к финансовым данным другого
пользователя.

### Category

Категория финансовой операции.

Примеры:

- Salary;
- Freelance;
- Food;
- Transport;
- Entertainment;
- Rent.

Категория относится либо к доходам, либо к расходам.

Пользователь может работать только со своими категориями.

### Transaction

Финансовая операция пользователя.

Операция содержит:

- пользователя;
- категорию;
- тип операции;
- сумму;
- описание;
- дату совершения;
- дату создания записи.

Бизнес-правила:

- сумма должна быть больше нуля;
- тип категории должен соответствовать типу операции;
- пользователь может использовать только собственную категорию;
- денежные значения хранятся с использованием decimal;
- удалённая или недоступная категория не должна использоваться
  для новой операции;
- пользовательская дата операции и границы финансовых периодов
  интерпретируются в часовом поясе Europe/Moscow (UTC+3);
- техническая дата создания записи хранится в UTC.

На первом этапе проект использует одну базовую валюту пользователя.
Конвертация валют не входит в MVP.

### Финансовая статистика

Статистика рассчитывается только по фактически зарегистрированным
операциям пользователя за выбранный период.

Основные показатели:

- общая сумма поступлений;
- общая сумма расходов;
- финансовый результат как разница между поступлениями и расходами;
- распределение поступлений и расходов по категориям.

Бизнес-правила:

- доходные операции учитываются только в сумме поступлений;
- расходные операции учитываются только в сумме расходов;
- положительный финансовый результат означает, что поступления
  превысили расходы;
- отрицательный финансовый результат означает, что расходы превысили
  поступления;
- одна операция учитывается только в категории, указанной в ней;
- расчёты всегда ограничиваются данными текущего пользователя.

Финансовый результат за период не является фактическим остатком на
банковском счёте: отдельные счета, кошельки и начальные остатки в этой
модели не учитываются.

## 5. MVP

Первая законченная версия должна включать:

### Авторизация

- регистрация;
- вход;
- JWT access token;
- refresh token;
- выход;
- получение текущего пользователя.

### Категории

- создание;
- просмотр списка;
- редактирование;
- удаление;
- разделение на категории доходов и расходов.

### Финансовые операции

- создание дохода или расхода;
- просмотр списка;
- редактирование;
- удаление;
- фильтрация по периоду;
- фильтрация по категории;
- фильтрация по типу;
- сортировка;
- пагинация.

### Dashboard

- сумма доходов за период;
- сумма расходов за период;
- финансовый результат за период;
- расходы по категориям;
- поступления по категориям;
- последние операции.

## 6. Что не входит в MVP

На первом этапе не реализуются:

- банковские интеграции;
- импорт банковских выписок;
- реальные платежи;
- конвертация валют;
- планирование расходов и месячные лимиты;
- совместные семейные аккаунты;
- социальные функции;
- мобильное приложение;
- микросервисы;
- Kubernetes;
- RabbitMQ;
- Redis;
- сложная event-driven архитектура.

Эти технологии могут быть добавлены только тогда, когда в проекте
появится реальная задача, которую они решают.

## 7. Архитектура backend

Backend строится как слоистый модульный монолит.

Проекты:

### Finance.Domain

Содержит:

- бизнес-сущности;
- value objects;
- перечисления;
- бизнес-правила;
- доменные ошибки.

Domain не должен зависеть от ASP.NET Core, EF Core, PostgreSQL или
React.

### Finance.Application

Содержит:

- use cases;
- команды и запросы;
- DTO;
- интерфейсы инфраструктуры;
- прикладную валидацию;
- координацию бизнес-операций.

Application зависит от Domain, но не зависит от конкретной базы данных.

### Finance.Infrastructure

Содержит:

- Entity Framework Core;
- FinanceDbContext;
- конфигурации сущностей;
- миграции;
- PostgreSQL;
- реализацию инфраструктурных интерфейсов;
- работу с refresh token;
- системное время и другие внешние зависимости.

Infrastructure может зависеть от Application и Domain.

### Finance.Api

Содержит:

- controllers;
- middleware;
- настройку авторизации;
- регистрацию зависимостей;
- конфигурацию приложения;
- преобразование HTTP-запросов и ответов.

Контроллеры должны быть тонкими. Они не должны содержать бизнес-логику
или прямую работу с базой данных.

## 8. Почему выбран модульный монолит

Модульный монолит выбран потому, что:

- проект разрабатывается одним человеком;
- предметная область пока небольшая;
- микросервисы не решают существующую проблему;
- монолит проще запускать, тестировать и развёртывать;
- внутри монолита всё равно можно сохранять чёткие границы;
- разработчик сможет сосредоточиться на бизнес-логике и данных.

Микросервисы не должны добавляться только ради демонстрации знания
микросервисов.

## 9. Почему используются Controllers

ASP.NET Core Controllers выбраны вместо Minimal API, потому что:

- они явно показывают устройство HTTP API;
- удобны для изучения model binding и filters;
- хорошо подходят для структурированного CRUD API;
- часто встречаются в продуктовых .NET-проектах;
- позволяют сохранить понятную границу между HTTP и Application.

Minimal API не считается плохим решением. Он просто не является
основным вариантом для этого учебного проекта.

## 10. Почему пока не используется MediatR

MediatR не используется на начальном этапе, потому что разработчик
должен сначала увидеть обычные зависимости и поток выполнения:

Controller → Application use case → Domain → Infrastructure.

Use case может быть представлен отдельным handler-классом, который
контроллер получает через dependency injection.

MediatR может быть рассмотрен позже, если появится реальная потребность
в pipeline behaviors, декораторных обработчиках или унифицированной
диспетчеризации команд.

## 11. Работа с данными

Основная база данных: PostgreSQL.

ORM: Entity Framework Core.

Правила:

- изменения схемы выполняются через миграции;
- связи и ограничения должны фиксироваться в базе данных;
- для денежных значений используется decimal;
- запросы на чтение не должны загружать лишние данные;
- необходимо избегать N+1 запросов;
- индексы добавляются под реальные сценарии запросов;
- пользовательские данные всегда фильтруются по идентификатору
  текущего пользователя;
- нельзя полагаться только на frontend для валидации и безопасности.

Generic Repository поверх EF Core не используется.

Специализированные интерфейсы доступа к данным допускаются, если они
выражают реальную потребность Application-слоя.

## 12. Архитектура frontend

Frontend строится на:

- React;
- TypeScript;
- Vite;
- React Router;
- TanStack Query;
- Axios;
- React Hook Form;
- Zod.

Frontend организуется по продуктовым функциям:

- auth;
- categories;
- transactions;
- dashboard.

Frontend отвечает за:

- пользовательский интерфейс;
- состояние форм;
- отображение загрузки и ошибок;
- вызов backend API;
- клиентскую валидацию для удобства пользователя.

Frontend не является доверенной стороной. Все критические проверки
повторяются на backend.

## 13. Docker

На раннем этапе через Docker запускается только PostgreSQL.

Backend и frontend запускаются локально, чтобы сохранить:

- быструю пересборку;
- hot reload;
- удобный debugger;
- простой просмотр логов.

После появления рабочего MVP будут созданы Dockerfile для backend и
frontend, а compose.yaml будет запускать всю систему.

## 14. Тестирование

Проект использует:

- unit tests для бизнес-правил Domain и Application;
- integration tests для API, EF Core и PostgreSQL;
- Testcontainers для интеграционных тестов;
- небольшое количество end-to-end тестов для основных сценариев.

Не требуется стремиться к формальному проценту покрытия.

В первую очередь тестируются:

- финансовые расчёты;
- правила доступа к данным;
- несовместимые категории и операции;
- агрегирование поступлений и расходов по периодам и категориям;
- ошибки валидации;
- авторизация;
- взаимодействие с настоящей PostgreSQL.

## 15. Порядок разработки

Проект развивается вертикальными срезами.

Каждый этап должен проходить через:

Frontend → API → Application → Domain → Infrastructure → PostgreSQL.

План этапов:

1. [x] Настройка репозитория и инструментов.
2. [x] PostgreSQL и FinanceDbContext.
3. [x] Health checks.
4. [x] Регистрация и авторизация.
5. [ ] **Следующий этап: категории.**
6. [ ] Финансовые операции.
7. [ ] Фильтрация и пагинация.
8. [ ] Dashboard и финансовая статистика.
9. [ ] Обработка ошибок и логирование.
10. [ ] Integration tests.
11. [ ] Полная контейнеризация.
12. [ ] CI.
13. [ ] Документация и подготовка проекта для резюме.

### Текущее состояние

Завершён сквозной срез регистрации и авторизации:

- доменные модели пользователя, категории и финансовой операции;
- PostgreSQL, FinanceDbContext, EF Core-конфигурации и миграции;
- health check базы данных;
- регистрация и вход по email и паролю;

Следующий вертикальный срез — управление пользовательскими категориями:

Codex не должен заранее реализовывать функциональность следующих

## 16. Критерий качественного решения

Решение считается качественным, если:

- оно решает текущую бизнес-задачу;
- его можно объяснить на собеседовании;
- оно не содержит ненужной архитектурной сложности;
- бизнес-правила защищены backend-кодом и базой данных;
- ошибки обрабатываются предсказуемо;
- код можно тестировать;
- проект собирается;
- тесты проходят;
- решение задокументировано;
- разработчик понимает путь данных через систему.

Главный вопрос при выборе архитектуры:

> Какую конкретную проблему решает это решение в текущем проекте?

Если конкретной проблемы нет, решение не должно добавляться только
потому, что оно популярно.
