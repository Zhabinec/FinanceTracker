# Finance Tracker

## 1. Назначение проекта

Finance Tracker представляет собой учебное full-stack приложение для
управления личными финансами.

Пользователь сможет:

- создавать учётную запись;
- регистрировать доходы и расходы;
- распределять операции по категориям;
- просматривать статистику;
- видеть, завершён ли выбранный период в плюс или в минус;
- анализировать структуру поступлений и расходов по категориям.

Это не просто демонстрационный CRUD. Проект должен постепенно показать
решение реальных backend-задач:

- проектирование бизнес-модели;
- хранение и целостность данных;
- аутентификация и авторизация;
- обработка ошибок;
- валидация;
- фильтрация и пагинация;
- транзакции;
- конкурентные изменения;
- тестирование;
- логирование;
- контейнеризация;
- взаимодействие backend и frontend.

## 2. Причина создания

Разработчик проекта имеет коммерческий опыт разработки на C# в Unity,
но хочет перейти в продуктовую backend-разработку на .NET.

Основная цель проекта:

- восстановить знания ASP.NET Core и PostgreSQL;
- изучить современную backend-разработку на .NET 10;
- вспомнить архитектурные решения и научиться объяснять их;
- получить практику разработки полного продукта;
- подготовить качественный проект для GitHub и резюме;
- подготовиться к собеседованиям на позиции C#/.NET Backend Developer.

Разработчику не требуется повторно изучать базовый синтаксис C#.
Основной фокус должен быть на backend-мышлении, данных, HTTP,
архитектуре, надёжности и бизнес-ограничениях.

## 3. Роль Codex

Codex разрешено использовать для генерации production-кода,
конфигурации, тестов, миграций и документации.

Codex не должен искусственно заставлять разработчика вручную писать
однотипный boilerplate-код ради обучения.

При этом Codex не должен без объяснения принимать важные
архитектурные решения.

Перед нетривиальной реализацией Codex должен:

1. Изучить существующий код и документацию.
2. Сформулировать задачу своими словами.
3. Определить бизнес-правила и возможные ошибки.
4. Предложить короткий план.
5. Объяснить важные архитектурные решения.
6. Указать альтернативы, если они действительно имеют значение.
7. Только после этого переходить к реализации.

После реализации Codex должен:

1. Показать, какие файлы были изменены.
2. Объяснить путь запроса через систему.
3. Объяснить, почему код расположен именно в этих слоях.
4. Указать потенциальные риски.
5. Запустить сборку и тесты.
6. Сообщить фактические результаты проверки.
7. Задать разработчику несколько вопросов по сделанному решению,
   если задача содержит важный учебный материал.

Codex должен помогать разработчику понимать систему, но не должен
намеренно замедлять разработку.

## 4. Продуктовая модель

### User

Зарегистрированный пользователь системы.

Основные данные:

- идентификатор;
- email;
- password hash;
- дата регистрации;
- базовая валюта.

Один пользователь не должен иметь доступ к финансовым данным другого
пользователя.

### Category

Категория финансовой операции.

Примеры:

- Salary;
- Freelance;
- Food;
- Transport;
- Entertainment;
- Rent.

Категория относится либо к доходам, либо к расходам.

Пользователь может работать только со своими категориями.

Бизнес-правила:

- название категории уникально внутри типа для одного пользователя
  без учёта регистра;
- тип категории не изменяется после создания;
- категория деактивируется вместо физического удаления, чтобы не
  разрушать историю финансовых операций;
- деактивированную категорию можно восстановить, но нельзя использовать
  для новой финансовой операции.

### Transaction

Финансовая операция пользователя.

Операция содержит:

- пользователя;
- категорию;
- тип операции;
- сумму;
- описание;
- дату совершения;
- дату создания записи.

Бизнес-правила:

- сумма должна быть больше нуля;
- тип категории должен соответствовать типу операции;
- пользователь может использовать только собственную категорию;
- денежные значения хранятся с использованием decimal;
- удалённая или недоступная категория не должна использоваться
  для новой операции;
- пользовательская дата операции и границы финансовых периодов
  интерпретируются в часовом поясе Europe/Moscow (UTC+3);
- техническая дата создания записи хранится в UTC.

На первом этапе проект использует одну базовую валюту пользователя.
Конвертация валют не входит в MVP.

### Финансовая статистика

Статистика рассчитывается только по фактически зарегистрированным
операциям пользователя за выбранный период.

Основные показатели:

- общая сумма поступлений;
- общая сумма расходов;
- финансовый результат как разница между поступлениями и расходами;
- распределение поступлений и расходов по категориям.

Бизнес-правила:

- доходные операции учитываются только в сумме поступлений;
- расходные операции учитываются только в сумме расходов;
- положительный финансовый результат означает, что поступления
  превысили расходы;
- отрицательный финансовый результат означает, что расходы превысили
  поступления;
- одна операция учитывается только в категории, указанной в ней;
- расчёты всегда ограничиваются данными текущего пользователя.

Финансовый результат за период не является фактическим остатком на
банковском счёте: отдельные счета, кошельки и начальные остатки в этой
модели не учитываются.

Первая законченная версия должна включать:

### Авторизация

- регистрация;
- вход;
- JWT access token;
- refresh token;
- выход;
- получение текущего пользователя.

### Категории

- создание;
- просмотр списка;
- редактирование;
- удаление;
- разделение на категории доходов и расходов.

### Финансовые операции

- создание дохода или расхода;
- просмотр списка;
- редактирование;
- удаление;
- фильтрация по периоду;
- фильтрация по категории;
- фильтрация по типу;
- сортировка;

- сумма доходов за период;
- сумма расходов за период;
- финансовый результат за период;
- расходы по категориям;
- поступления по категориям;
- последние операции.

## 6. Что не входит в MVP

На первом этапе не реализуются:

- банковские интеграции;
- импорт банковских выписок;
- реальные платежи;
- конвертация валют;
- планирование расходов и месячные лимиты;
- совместные семейные аккаунты;
- социальные функции;
- мобильное приложение;
- микросервисы;
- Kubernetes;
- RabbitMQ;
- Redis;
- сложная event-driven архитектура.

Эти технологии могут быть добавлены только тогда, когда в проекте
появится реальная задача, которую они решают.

## 7. Архитектура backend

Backend строится как слоистый модульный монолит.

Проекты:

### Finance.Domain

Содержит:

- бизнес-сущности;
- value objects;
- перечисления;
- бизнес-правила;
- доменные ошибки.

Domain не должен зависеть от ASP.NET Core, EF Core, PostgreSQL или
React.

### Finance.Application

Содержит:

- use cases;
- команды и запросы;
- DTO;
- интерфейсы инфраструктуры;
- прикладную валидацию;
- координацию бизнес-операций.

Application зависит от Domain, но не зависит от конкретной базы данных.

### Finance.Infrastructure

Содержит:

- Entity Framework Core;
- FinanceDbContext;
- конфигурации сущностей;
- миграции;
- PostgreSQL;
- реализацию инфраструктурных интерфейсов;
- работу с refresh token;
- системное время и другие внешние зависимости.

Infrastructure может зависеть от Application и Domain.

### Finance.Api

Содержит:

- controllers;
- middleware;
- настройку авторизации;
- регистрацию зависимостей;
- конфигурацию приложения;
- преобразование HTTP-запросов и ответов.

Контроллеры должны быть тонкими. Они не должны содержать бизнес-логику
или прямую работу с базой данных.

## 8. Почему выбран модульный монолит

Модульный монолит выбран потому, что:

- проект разрабатывается одним человеком;
- предметная область пока небольшая;
- микросервисы не решают существующую проблему;
- монолит проще запускать, тестировать и развёртывать;
- внутри монолита всё равно можно сохранять чёткие границы;
- разработчик сможет сосредоточиться на бизнес-логике и данных.

Микросервисы не должны добавляться только ради демонстрации знания
микросервисов.

## 9. Почему используются Controllers

ASP.NET Core Controllers выбраны вместо Minimal API, потому что:

- они явно показывают устройство HTTP API;
- удобны для изучения model binding и filters;
- хорошо подходят для структурированного CRUD API;
- часто встречаются в продуктовых .NET-проектах;
- позволяют сохранить понятную границу между HTTP и Application.

Minimal API не считается плохим решением. Он просто не является
основным вариантом для этого учебного проекта.

## 10. Почему пока не используется MediatR

MediatR не используется на начальном этапе, потому что разработчик
должен сначала увидеть обычные зависимости и поток выполнения:

Controller → Application use case → Domain → Infrastructure.

Use case может быть представлен отдельным handler-классом, который
контроллер получает через dependency injection.

MediatR может быть рассмотрен позже, если появится реальная потребность
в pipeline behaviors, декораторных обработчиках или унифицированной
диспетчеризации команд.

## 11. Работа с данными

Основная база данных: PostgreSQL.

ORM: Entity Framework Core.

Правила:

- изменения схемы выполняются через миграции;
- связи и ограничения должны фиксироваться в базе данных;
- для денежных значений используется decimal;
- запросы на чтение не должны загружать лишние данные;
- необходимо избегать N+1 запросов;
- индексы добавляются под реальные сценарии запросов;
- пользовательские данные всегда фильтруются по идентификатору
  текущего пользователя;
- нельзя полагаться только на frontend для валидации и безопасности.

Generic Repository поверх EF Core не используется.

Специализированные интерфейсы доступа к данным допускаются, если они
выражают реальную потребность Application-слоя.

- React Hook Form;

Frontend организуется по продуктовым функциям:

Frontend отвечает за:

- клиентскую валидацию для удобства пользователя.

Frontend не является доверенной стороной. Все критические проверки
повторяются на backend.

## 13. Docker

На раннем этапе через Docker запускается только PostgreSQL.

Backend и frontend запускаются локально, чтобы сохранить:

- быструю пересборку;
- hot reload;
- удобный debugger;
- простой просмотр логов.

После появления рабочего MVP будут созданы Dockerfile для backend и
frontend, а compose.yaml будет запускать всю систему.

## 16. Критерий качественного решения

Решение считается качественным, если:

- оно решает текущую бизнес-задачу;
- его можно объяснить на собеседовании;
- оно не содержит ненужной архитектурной сложности;
- бизнес-правила защищены backend-кодом и базой данных;
- ошибки обрабатываются предсказуемо;
- код можно тестировать;
- проект собирается;
- тесты проходят;
- решение задокументировано;
- разработчик понимает путь данных через систему.

Главный вопрос при выборе архитектуры:

> Какую конкретную проблему решает это решение в текущем проекте?

Если конкретной проблемы нет, решение не должно добавляться только
потому, что оно популярно.

## 17. Расширение продукта после MVP

По прямому запросу разработчика от 25.10.2026 согласовано расширение
приложения за рамки первого MVP. Ограничения раздела 6 описывают
первый MVP и не запрещают перечисленные ниже новые этапы.

Порядок реализации и проверки:

1. [x] Восстановление пароля по email: одноразовые токены с ограниченным сроком,
   одинаковый ответ для существующего и неизвестного email, отзыв сессий.
   По уточнению разработчика добавлено обязательное подтверждение email
   отдельной одноразовой ссылкой, повторная отправка и явная почтовая
   имитация через Mailpit. Письма указывают email аккаунта.
2. [x] Счета: валюта, начальный остаток, архивирование, баланс и переводы.
   Первый срез: создание и переименование счетов в базовой валюте,
   архивирование и восстановление, выбор счёта в операциях и фильтр истории.
   Баланс рассчитывается по всей записанной истории, включая будущие даты;
   отрицательный баланс допустим. Начальный остаток и валюта неизменяемы.
   Переводы между своими активными счетами в одной валюте реализованы отдельной
   атомарной записью, с защитой повторной отправки и отменой с сохранением истории.
3. [ ] Валюты: исходная сумма, сохранённый курс и сумма в базовой валюте;
   обновление справочных курсов не меняет историю.
   По уточнению разработчика сначала реализуется только переключение валюты
   отображения RUB/USD/EUR по справочному курсу ЦБ. Регистрация не предлагает
   валюту: сервер использует RUB по умолчанию. Переключение не меняет валюту
   пользователя, счетов и записанные суммы; ввод остаётся в исходной валюте.
   При недоступности курса показываются исходная валюта и явное сообщение.
   Реальный обмен и счета в разных валютах отложены.

4. [x] Бюджеты по месяцу и расходной категории в базовой валюте пользователя.
   В обзоре: лимит, фактические расходы за весь месяц, остаток и превышение;
   изменение и удаление с optimistic concurrency. Неактивные категории
   сохраняют историю и допускают настройку лимита для прошлых месяцев.
5. [x] CSV-импорт с сопоставлением колонок, предпросмотром, валидацией и
   защитой от повторного применения. Прямой XLSX-импорт пока не требуется:
   пользователь согласовал CSV как первый формат для Excel и других программ.
   Импорт в журнале: UTF-8/Windows-1251, CSV/TSV до 1000 операций;
   категории сопоставляются с существующими по названию и типу.
   Весь файл и отметка применения сохраняются одной транзакцией.
   Повтор того же содержимого блокируется по SHA256 на пользователя;
   другой изменённый файл с пересекающимися операциями автоматически не объединяется.
6. [x] Подготовка внешнего развёртывания: HTTPS, секреты, резервное копирование,
   восстановление и обновление. Покупка хостинга требует выбора пользователя.
   Добавлены отдельный compose.production.yaml, nginx TLS, настройки настоящей
   почты и проверенные локально backup/restore-скрипты. Порядок размещения —
   docs/deployment.md. Публичное размещение и реальная доставка почты ожидают
   выбранных домена, сервера, сертификата и учётных данных провайдера.

Уточнение UX: основной быстрый ввод — нажатие активной категории и модальное
окно с названием и суммой. Тип и категория подставляются, дата добавления
определяется сервером по Москве. Счёт выбирается автоматически (последний
активный выбранный, затем основной, затем первый активный); выбор другого
счёта доступен отдельно. После сохранения доступна отмена добавления.
По уточнению разработчика раздел «Операции» переименован в «История»:
только просмотр, фильтры, исправление и удаление. Дублирующая форма создания
«Запись с датой» и переход «Добавить по категории» удалены. Добавление выполняется
через категории; дату можно исправить при редактировании записи в истории.
Импорт находится в свёрнутом блоке после списка. Пагинация видна только при
нескольких страницах. URL /transactions и серверный API сохранены.
Адаптивный интерфейс: вся активная плашка категории открывает быстрый ввод,
управление вынесено в отдельную кнопку. На телефоне — две карточки в ряд,
крупные области нажатия и окно ввода у нижнего края экрана.
Все пять разделов используют общую оболочку с постоянной навигацией:
на телефоне панель находится снизу, на ПК — сверху. Выход — отдельная
компактная иконка. В обзоре итоги идут раньше настроек; расширенные формы
и фильтры раскрываются явно. Учитываются динамическая высота viewport и
safe-area для мобильных браузеров и будущего Telegram Mini App; подключение
Telegram SDK и авторизация через Telegram пока не входят в этот срез.
По уточнению UX от 26.10.2026 технические пояснения о часовом поясе, источнике
курсов и внутренних расчётах остаются в документации. Общий переключатель
валюты рядом с заголовком показывает только RUB/USD/EUR; постоянная большая
панель и пояснительные абзацы убраны. Ошибки и подсказки, нужные для ввода, сохраняются.

По решению разработчика от 26.10.2026 идея локального хранения и E2EE-синхронизации
отложена. Продолжается развитие текущего слоистого монолита с PostgreSQL;
перестройка хранения под local-first сейчас не выполняется.

По запросу подготовки к показу и размещению от 26.10.2026:
- обычные доходы/расходы защищаются requestId на пользователя; повтор не создаёт
  дубль, не меняет дату, не восстанавливает удалённую запись. Старые API-клиенты
  без ключа остаются совместимыми; текущий интерфейс всегда отправляет ключ;
- регистрация создаёт семь обычных собственных категорий вместе с пользователем
  и основным счётом. Существующие пользователи получают набор только при
  полностью пустом списке. Настроенные и архивные категории не меняются;
- миграции проверяются на чистой БД и при обновлении прежней схемы;
- сценарий демонстрации и границы проверки публикации описаны в docs/demo.md.

Инварианты расширения:

- счёт и категория принадлежат текущему пользователю;
- валюта счёта не меняется после появления финансовой истории;
- баланс = начальный остаток + доходы - расходы + входящие переводы - исходящие;
- перевод между своими счетами атомарен и не является доходом или расходом;
- денежные суммы и курсы используют decimal, HTTP передаёт их строками;
- для отчётности сохраняется базовая сумма операции на дату её записи;
- импорт не доверяет владельцу и суммам из файла и не применяется частично;
- бюджеты учитывают фактические расходы, включая импорт, без переводов;
- восстановление пароля не раскрывает токен в API-ответе или логах.

Архитектура остаётся слоистым монолитом. Будущий Telegram Mini App или
бот — дополнительный клиент/адаптер; Domain и Application не зависят
от Telegram SDK, React и способа доставки уведомлений. Привязка Telegram
должна подтверждаться сервером; переданный клиентом Telegram user id не
является доказательством личности. Реализация Telegram-клиента в текущий
этап не входит, но общие финансовые сценарии должны быть пригодны для него.

## 18. Ветки платформ

По запросу разработчика от 26.10.2026:

- `main` — общая стабильная основа и точка сборки релизов;
- `codex/platform-web` — браузерная версия с адаптацией под телефон;
- `codex/platform-telegram` — подготовленная ветка для Telegram Mini App.

Все три ветки начинаются с одного проверенного релиз-кандидата. Создание ветки
Telegram не означает, что Telegram SDK или вход через Telegram уже реализованы.
Backend, Domain, Application и бизнес-правила остаются общими. Общие исправления
вносятся в `main` через отдельные ветки и PR, затем переносятся обычным merge
в платформенные ветки. Финансовая модель не копируется под каждую платформу.
Самостоятельный нативный клиент Android/iOS в этот запрос не входит.
В Telegram-ветке начата настройка бота: `scripts/configure-telegram.ps1` проверяет
getMe и сохраняет новый токен в локальных .NET User Secrets, не в репозитории.
Подробности и следующие этапы — docs/telegram.md. Сохранение токена само по себе
ещё не реализует Telegram-вход или публикацию Mini App.

## 19. Подключение Telegram в платформенной ветке

По запросу разработчика подключается Telegram Mini App как дополнительный клиент
того же монолита. Выбран общий существующий подтверждённый email-аккаунт:
разовая явная привязка через email/пароль и подписанный Telegram initData,
затем автоматический вход. Отдельная регистрация без email и фиктивные email
не входят в этот этап. Финансовая модель и правила владения остаются общими.

Привязка уникальна с обеих сторон, не заменяется молча. На сервере проверяются
подпись и срок initData. Отключение в профиле немедленно отзывает Telegram-доступ
по версии привязки; повторная привязка не оживляет старые JWT. Refresh Telegram
вращается и хранится клиентом в памяти, независимо от браузерных cookies.
Порядок блокировок user → session сохраняется для совместимости со сбросом пароля.
Перенос инфраструктуры на отдельные сервисы и новые production-зависимости не нужен.

Описание потока и публикации — docs/telegram.md. Публичный HTTPS-хостинг ещё
требуется выбрать; до размещения и настройки Main Mini App в BotFather бот
не считается опубликованным приложением. Проверка SDK в E2E использует имитацию;
реальные Telegram Web/Desktop/телефон нужно проверить после публикации.

По запросу от 26.10.2026 готовится бесплатное размещение Render + Neon:
один Web Service отдаёт frontend и API, PostgreSQL размещается отдельно.
Регион серверов не меняет бизнес-часовой пояс Europe/Moscow (UTC+3).
Перед публичным запуском добавляются ограничения частоты регистрации/входа,
общего числа API-запросов, параллелизма и размеров тела запроса.

Разработчик повторно поднял требование приватности финансовых записей.
Публичная отправка финансовой истории отложена до выбора модели хранения.
Предложение клиентского шифрования описано в docs/decisions/private-financial-vault.md;
оно ещё не реализовано и не меняет текущие гарантии PostgreSQL-модели.
Перенос финансовых расчётов на клиент и управление ключом требуют отдельного
согласованного этапа; существующие данные не удаляются и не мигрируются молча.
