# Спецификация Finance Tracker

## Назначение

Finance Tracker — приложение для личного учёта доходов и расходов с Telegram Mini App и адаптивным браузерным интерфейсом. Оно показывает финансовый результат периода, структуру расходов, остатки на счетах и выполнение бюджетов. Финансовые записи шифруются на клиенте и синхронизируются через API.

Этот документ определяет действующую продуктовую модель и архитектурные границы. Запуск описан в [README](README.md), сценарии работы — в [руководстве пользователя](docs/user-guide.md).

## Доступ и первый запуск

- Основной способ входа — подписанный запуск Telegram Mini App.
- Google OpenID Connect доступен в обычном браузере.
- Email-регистрация по умолчанию доступна только с Mailpit. Для других провайдеров её можно явно включить настройкой Auth:EmailRegistrationEnabled.
- Существующий парольный вход сохраняется на /login/password без ссылки с публичного экрана.
- Создание Telegram-аккаунта требует явного действия. Открытие бота само по себе не создаёт аккаунт.
- Регистрация создаёт основной счёт и семь собственных категорий: продукты, транспорт, дом, здоровье, развлечения, зарплата, подработка.
- Новая история не содержит демонстрационных расходов, доходов и остатков.
- Аккаунты не объединяются по совпадению email. Привязка провайдера к существующей истории должна быть явной.
- Telegram-only аккаунт не имеет email и пользовательского пароля. Перенос такого аккаунта в браузер через привязку Google не реализован.

## Финансовая модель

| Объект | Содержание |
|---|---|
| Пользователь | Идентификатор, необязательный email, сведения об аутентификации, базовая валюта |
| Категория | Название, тип Income/Expense, активность и версия |
| Счёт | Название, валюта, начальный остаток, архивность и версия |
| Операция | Счёт, категория, тип, положительная сумма, название/описание, дата и версия |
| Перевод | Два собственных счёта, сумма, дата, идентификатор запроса и состояние отмены |
| Бюджет | Расходная категория, календарный месяц, лимит и версия |
| Приватное хранилище | Один зашифрованный финансовый документ с ревизией на пользователя |

### Инварианты

1. Счета, категории и записи принадлежат одному пользователю. Backend проверяет владельца хранилища и legacy-записей.
2. Тип категории не меняется; название уникально внутри типа без учёта регистра.
3. Категория деактивируется с сохранением истории. Новую запись в неактивной категории создать нельзя.
4. Сумма дохода, расхода, перевода и лимита положительная; деньги не рассчитываются через float.
5. Тип операции совпадает с типом категории; счёт должен быть активным.
6. Баланс счёта = начальный остаток + доходы − расходы + входящие переводы − исходящие переводы.
7. Перевод выполняется между разными активными счетами в одной валюте. Он атомарно влияет на оба остатка и не считается доходом или расходом.
8. Валюта счёта не меняется после появления истории; архивирование сохраняет записи.
9. Результат периода = доходы − расходы. Он не равен сумме остатков на счетах.
10. Бюджет учитывает расходы своей категории за месяц, включая импорт; переводы исключены.
11. Изменение записи проверяет версию; устаревшие данные не перезаписываются молча.
12. Повтор сохранения с тем же идентификатором запроса не создаёт вторую запись. Удалённая запись не восстанавливается повторной отправкой.
13. Импорт применяется целиком после проверки всех строк. Повтор того же нормализованного файла блокируется.
14. Календарные даты операций и отчётные периоды используют Europe/Moscow; технические timestamps — UTC. Допустимые годы операций: 1900–9998.

В приватной модели суммы хранятся строками и рассчитываются через BigInt-копейки. Legacy backend использует decimal и PostgreSQL numeric(18,2).

## Интерфейс

- Категории: вся плашка открывает быстрый ввод названия и суммы; дата назначается автоматически.
- История: просмотр, фильтры, сортировка, пагинация, исправление и удаление.
- Обзор: итоговые суммы, распределение по категориям, бюджеты и последние записи.
- Кольцевая диаграмма отображается только при расходах в выбранном периоде. Доходы и переводы в неё не входят.
- Счета: создание, переименование, архивирование, начальные остатки и переводы.
- Импорт: CSV/TSV, сопоставление колонок, предпросмотр и атомарное применение.
- Переключатель RUB/USD/EUR меняет только отображение по курсу; сохранённые суммы и валюты счетов не меняются.
- Новый счёт приватного интерфейса получает базовую валюту хранилища автоматически; произвольный выбор валюты счёта в интерфейсе не предлагается.
- Навигация и области нажатия адаптированы для телефона и компьютера. Короткие CSS-анимации отключаются при prefers-reduced-motion.

## Приватность и синхронизация

Финансовый документ шифруется AES-256-GCM на клиенте. Сервер не получает ключ, PIN и открытые суммы, названия или описания приватной истории. Он хранит шифротекст, владельца, ревизию и служебные метаданные.

Код восстановления содержит случайный финансовый ключ. PIN из шести цифр сохраняет на доверенном устройстве только зашифрованный код в IndexedDB. Вход через провайдера не заменяет разблокировку хранилища. Потерянный финансовый ключ не восстанавливается сбросом пароля.

Синхронизация требует соединения с сервером. Конфликты ревизий и неопределённый результат сохранения требуют явного разрешения; история не заменяется пустой копией. Старые серверные записи удаляются из рабочих таблиц только после проверенного переноса в приватное хранилище. Старые дампы и WAL не шифруются задним числом.

Подробная модель и ограничения: [приватное хранилище](docs/decisions/private-financial-vault.md).

## Архитектурные границы

Backend — слоистый модульный монолит. Domain не зависит от ASP.NET Core, EF Core и интерфейса. Application координирует серверные сценарии через специализированные интерфейсы. Infrastructure реализует PostgreSQL, криптографическую проверку провайдеров и доставку писем. API отвечает за HTTP и аутентификацию.

Финансовые действия приватного интерфейса выполняются клиентским ledger; сервер не может проверить арифметику внутри шифротекста. Он проверяет авторизацию, владельца, размер envelope, ревизии и согласованность миграции. Это отдельная граница доверия, а не дублирование финансовых расчётов на сервере.

Схема БД меняется EF Core migrations. Асинхронные серверные операции сохраняют CancellationToken. Секреты хранятся вне Git. Приложение не использует микросервисы, брокеры сообщений и распределённый cache.

## Размещение и ветки

Публичный тестовый контур: Render Web Service с frontend и API в одном origin; PostgreSQL размещён в Neon. Бот открывает тот же HTTPS-сайт внутри Telegram.

- main — стабильная общая версия.
- codex/platform-telegram — ветка публикации текущего Render-сервиса.
- codex/platform-web — платформенная ветка браузерного клиента.

Текущий сервис обновляется вручную после CI. Blueprint render.yaml описывает отдельный способ создания окружения и не включает автоматический деплой существующего сервиса.

## Проверка качества

Серверные изменения проверяются сборкой и unit/integration-тестами; frontend — тестами, lint и production build; основные сценарии — Playwright. Интеграционные проверки используют временную PostgreSQL, а не пользовательскую БД. Проверка backup включает восстановление в отдельную БД.

Приоритет проверки: владение данными, деньги, конкурентное редактирование, повторные запросы, аутентификация, перенос и восстановление зашифрованной истории. Команды и границы автоматизации: [тестирование](docs/testing.md).

## Ограничения

Нет банковских интеграций, реальных платежей, обмена валют, совместных бюджетов, нативного мобильного приложения, автоматического объединения аккаунтов, прямого XLSX-импорта и полноценного offline-first режима.

Размер открытого финансового JSON ограничен 2 000 000 байт; списки также имеют лимиты. PIN не защищает от офлайн-перебора украденного профиля так же хорошо, как случайный код. Шифрование не защищает от вредоносного кода на разблокированном устройстве или подмены клиентского приложения. Бесплатный тестовый хостинг не гарантирует постоянную доступность.
