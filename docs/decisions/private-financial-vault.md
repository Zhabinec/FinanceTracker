# Приватное финансовое хранилище, формат 1

Статус: реализовано по запросу разработчика от 27.10.2026. Публичный деплой
отдельно не выполнен. Старый аккаунт становится приватным после явного переноса
в интерфейсе; до переноса его прежние строки PostgreSQL остаются открытыми.

## Реализованный поток

1. После обычного или Telegram-входа интерфейс блокирует финансовые страницы
   до настройки или разблокировки хранилища.
2. Клиент получает согласованный экспорт своей старой истории и генерирует
   случайный 256-битный ключ. Код FT1 содержит этот ключ и контрольную сумму
   от опечаток. Это не пароль и не хеш Telegram ID; перебор слабого пароля
   хранилища не используется. После импорта ключа CryptoKey неэкспортируемый.
3. Пользователь сохраняет код и явно разрешает перенос. Клиент шифрует документ
   AES-256-GCM с новым случайным 96-битным nonce, 128-битным tag и AAD,
   связывающей версию формата, владельца, ID хранилища и ревизию.
4. `POST /api/private-finance/stage` сохраняет pending-копию. Старые строки пока
   остаются. Любые старые финансовые API для этого пользователя уже блокируются.
5. Клиент скачивает сохранённый шифротекст и сверяет расшифрованное содержимое
   с экспортом. Только после успешной проверки вызывает `/activate`.
   Сервер повторно сверяет fingerprint исходного экспорта; затем в одной
   транзакции удаляет открытые финансовые строки и активирует хранилище.
   При сбое транзакции открытая история остаётся; незавершённый перенос можно отменить.
6. Счета, операции, переводы, категории, бюджеты, CSV и отчёты обслуживает
   клиентский ledger. Деньги представлены строками и целыми копейками BigInt;
   плавающая арифметика для денег не применяется. Исходный CSV серверу не отправляется.
7. `PUT /api/private-finance` получает только зашифрованный документ, ожидаемую
   ревизию и mutation ID. Два устройства не могут молча затереть одну ревизию.
   Точный повтор последней записи идемпотентен. Ключ и код не входят в HTTP payload.

На пользователя хранится один текущий документ, не больше 2 000 000 байт
открытого JSON плюс GCM tag; без неограниченной истории серверных версий.
Списки внутри документа также ограничены. Слишком большая старая история
отклоняется до переноса без усечения и удаления; для неё нужен отдельный сценарий.

Ключ остаётся в памяти текущей вкладки и очищается логически при выходе,
блокировке и смене аккаунта. Расшифрованные финансовые query caches тоже очищаются.
После перезагрузки нужен сохранённый код. Автозапоминание ключа через Telegram
SecureStorage в этой версии не включено; нет скрытого отката к открытому localStorage.
Стандартный браузерный код не может гарантировать физическое затирание всех копий
из RAM устройства или защиту от скомпрометированного браузера.
Настройки доступа к аккаунту, смена пароля и отключение Telegram доступны
из заблокированного экрана без финансового ключа.

После неясного результата записи ciphertext сохраняется в sessionStorage
до подтверждения в пределах жизни вкладки. Перезагрузка сохраняет его,
а закрытие вкладки может удалить; перед закрытием нужно скачать копию.
Открытые данные и ключ туда не помещаются. Пользователь может
повторить сохранение, скачать зашифрованную копию или явно вернуться к версии
на сервере. Конфликт не приводит к автоматическому перезаписыванию данных.

В профиле доступны скачивание и явное восстановление зашифрованной копии.
Восстановление создаёт новую серверную ревизию и требует подтверждения замены
текущей истории. На экране разблокировки есть восстановление из файла с кодом,
даже если текущий серверный ciphertext повреждён. Копия привязана к текущему
пользователю и ID хранилища; перенос файла в другой аккаунт не реализован.

Согласованность обеспечивается PostgreSQL session advisory locks на пользователя:
старые чтения берут shared lock, записи и vault-запросы — exclusive. Соединение
удерживается через транзакции store; cancellation сохраняется, unlock ограничен
таймаутом. Нужен direct endpoint PostgreSQL/Neon, без transaction pooling и
без Npgsql Multiplexing. Это работает между экземплярами API без Redis.

Контроллеры передают сценарии Application; Domain валидирует ограниченный
непрозрачный envelope, Infrastructure отвечает за PostgreSQL и атомарный перенос.
Сервер не может проверить финансовые правила внутри ciphertext. Старые Domain
сценарии сохранены для миграции и совместимости legacy API, но приватному аккаунту
эти API недоступны. Проверки приватного ledger отдельно покрываются клиентскими тестами.

## Требование

Утечка серверной БД и её резервных копий не должна раскрывать суммы, описания,
названия категорий, счетов, бюджетов и переводы. Администратору сервера не нужен
ключ чтения финансовой истории. Браузер и Telegram должны открывать одно хранилище.

## Обоснование криптографической модели

Клиент генерирует случайный ключ финансового хранилища и шифрует содержимое
AES-256-GCM средствами Web Crypto до отправки. Для каждого шифрования нужен
новый уникальный nonce; идентификатор хранилища и версия формата связываются с
шифротекстом через authenticated additional data. Base64 используется только
для передачи байтов, он не обеспечивает конфиденциальность.

Сервер хранит владельца, ограниченный по размеру зашифрованный документ,
версию формата, ревизию синхронизации, nonce и authentication tag.
Счета, категории, бюджеты и записи входят внутрь зашифрованного документа.
Суммы, валюты, описания и названия не дублируются открытыми поисковыми полями.
Не хранить полные initData, профиль Telegram, исходные CSV и открытые финансовые
документы в логах, аналитике или отчётах об ошибках.

Ключ не равен Telegram ID, токену бота, JWT или паролю входа. Удобный вход через
Telegram сам по себе не расшифровывает историю на новом устройстве.
Для первого варианта перенос выполняется с помощью высокоэнтропийного кода
восстановления, выдаваемого только пользователю. Вариант отдельного пароля
хранилища требует соль, стойкий KDF, шифрование ключа и версионирование параметров;
параметры KDF и совместимость WebView необходимо отдельно проверить до реализации.

Возможное запоминание ключа через Telegram SecureStorage — отдельное будущее
улучшение с проверкой поддержки клиентом и явным согласием пользователя.
В текущей версии разблокированный ключ остаётся в памяти, без отката к
открытому localStorage.

Запись: ввод → проверка финансовых правил на клиенте → шифрование → отправка
зашифрованного документа с ожидаемой ревизией → проверка владельца и квоты
на сервере → атомарное сохранение. Несовпадение ревизии даёт конфликт, а не
затирает более новые данные. Сеть, повторы запросов и ошибочная расшифровка
не должны заменять историю пустым документом.

## Изменение обязанностей приложения

Сервер не выполняет SQL-отчёты, фильтры и бюджетные расчёты над
закрытыми суммами. Финансовые расчёты, импорт, проверки баланса и отображение
работают в клиентском модуле с точной арифметикой денег. Сервер продолжает
отвечать за аккаунты, подтверждение входа, владение, квоты и синхронизацию.
Открытые текущие финансовые API нельзя оставлять запасным путём сохранения
для приватного аккаунта. Смешанные режимы требуют явного разграничения.

Размер документа, частота запросов и число серверных версий ограничены.
Синхронизация — онлайн с явным разрешением конфликта, без обещания
автоматического слияния произвольных офлайн-изменений.

## Границы защиты

- Утечка текущего приватного документа БД, логического дампа после переноса и
  серверных ключей авторизации не раскрывает финансовые записи,
  если ключ хранилища никогда не покидал клиент.
- Email, Telegram ID, существование аккаунта, размер и время синхронизации остаются
  видны серверу. Скрывать их этим решением не обещаем.
- Потеря всех устройств и кода восстановления означает потерю расшифровки.
  Сброс пароля аккаунта по email не восстанавливает финансовый ключ.
- Заражённое устройство, XSS или подмена загружаемого frontend могут перехватить
  разблокированные данные. Клиентское шифрование само по себе от этого не защищает.
- Шифрование не предотвращает удаление данных и DDoS. Для доступности отдельно
  нужны лимиты, резервные копии и защита инфраструктуры.
- Старые дампы, WAL, физические снимки и удалённые версии, созданные до переноса,
  не шифруются задним числом. Их хранение и удаление — отдельная процедура;
  приложение не обещает стереть прежние открытые данные из чужих копий.
- Сервер видит владельца, размер и время синхронизации. Подмена серверного frontend
  может перехватить ключ при следующем вводе; это не защита от активного вредоносного
  издателя кода. Откат старой валидной копии можно заметить по запомненной ревизии
  в текущей сессии, но независимой защиты от rollback на новом устройстве здесь нет.

## Рассмотренные альтернативы

- Шифрование ключом на сервере проще сохранить в нынешней архитектуре и полезно
  против отдельной утечки дампа. Компрометация сервера с ключом сохраняет риск чтения.
- Telegram DeviceStorage локален и ограничен 5 МБ; он не даёт синхронизацию с обычным
  браузером и требует резервного копирования на случай потери устройства.
- Telegram CloudStorage ограничен 1024 ключами по 4096 символов и не объявлен
  сквозным шифрованным хранилищем. Подходит для небольших настроек; не выбираем
  основным финансовым хранилищем между Telegram и браузером.
- SecureStorage предназначен для небольшого числа секретов (до 10 элементов),
  а не всей истории операций.

## Проверки до публичного запуска

Изменение одного байта шифротекста, nonce или AAD должно отвергаться.
Проверяются неверный ключ, повтор nonce, чужой владелец, превышение квоты,
повтор записи, конфликт двух устройств, потеря соединения и восстановление
резервной копии на новом устройстве. В сетевых запросах и дампе не должно быть
тестовых открытых сумм и описаний. Старые данные не удаляются автоматически:
миграция требует резервной копии и проверки расшифровки результата.
