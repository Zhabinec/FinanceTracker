# Как показать Finance Tracker

Сценарий на несколько минут для нового аккаунта. Не требует заполненной базы,
банковских подключений или объяснения внутренних настроек.

1. Зарегистрироваться и подтвердить email. Локально письмо приходит в Mailpit
   на http://localhost:8025; на публичной версии нужен настроенный почтовый провайдер.
2. Открыть «Категории»: уже есть продукты, транспорт, дом, здоровье, развлечения,
   зарплата и подработка. Все категории принадлежат новому пользователю и редактируются.
3. Нажать «Зарплата», ввести название «Аванс» и сумму 30 000. Затем нажать
   «Продукты» и добавить «Покупки» на 450. В обоих случаях нужны только два поля.
4. В «Истории» показать доход/расход, фильтр, исправление записи и удаление.
   Дата добавляется автоматически, при необходимости её можно исправить.
5. В «Обзоре» показать итоги и добавить месячный бюджет «Продукты» на 5 000:
   потрачено 450, осталось 4 550. Выбор USD/EUR меняет только отображение сумм.
6. В «Счетах» создать второй счёт и перевести на него деньги. Перевод меняет
   два остатка, а доход и расход в обзоре сохраняются. Показать отмену перевода.
7. При необходимости раскрыть CSV-импорт в истории: выбрать колонки, показать
   предпросмотр ошибок, затем применить исправленный файл. Есть скачиваемый пример.

Для регулярного показа лучше создавать отдельные демонстрационные аккаунты,
не помещать пароли или реальные финансовые данные в README, screenshots и Git.
Стартовый набор не содержит фиктивных доходов, расходов или остатков.

## Что объяснять разработчику

- Controller преобразует HTTP и вызывает Application; правила денег и владельца
  находятся в Domain и повторно защищаются связями/ограничениями PostgreSQL.
- Запись и отметка запроса сохраняются одной транзакцией. Уникальный ключ
  `(UserId, RequestId)` закрывает гонку двух отправок. Повтор после потери ответа
  возвращает одну запись; изменение данных с тем же ключом даёт 409.
- Версия записи защищает редактирование; это другая задача, чем повторная отправка.
- Балансы, бюджеты и обзор считаются по одним финансовым записям; переводы отдельно.
- Регистрация атомарно создаёт пользователя, основной счёт и стартовые категории.
- Миграция проверяется и на чистой БД, и на старой схеме. Backup проверяется восстановлением.

## Перед публикацией

Сборка, unit/integration и браузерные проверки должны быть зелёными на commit релиза.
Локальный прогон не заменяет GitHub Actions. Для релиза сохранить ссылку на
успешный Actions run и убедиться, что его head commit совпадает с публикуемой
версией. При падении e2e изучить аннотации GitHub reporter и приложенный отчёт
Playwright; один успешный build не подтверждает пользовательский сценарий.

Публичный адрес, настоящая почта, сертификат и расписание backup настраиваются
по [deployment.md](deployment.md). Конфигурация сама по себе не означает публикацию.
