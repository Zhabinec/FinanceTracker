# Безопасность

## Модель данных

Сервер хранит аккаунты, провайдерные привязки, хеши сессионных и почтовых токенов, служебные метаданные и зашифрованные финансовые документы. Email Telegram-only аккаунта равен NULL; фиктивные адреса не создаются.

Ключ и PIN финансов не отправляются серверу. Сервер проверяет владельца envelope и доступ, но не денежные инварианты внутри ciphertext. Открытые legacy-записи защищены авторизацией и ограничениями БД до переноса.

Границы AES-GCM, PIN, метаданных и старых backup описаны в [модели приватного хранилища](decisions/private-financial-vault.md). Шифрование не гарантирует защиту от любых атак.

## Аутентификация

- JWT проверяется по подписи, сроку, issuer/audience и security stamp.
- Telegram initData проверяется HMAC и сроком; initDataUnsafe и user id не считаются доказательством входа.
- Telegram-привязка имеет версию, проверяемую на каждом запросе. Единственный способ входа Telegram-only аккаунта отключить нельзя.
- Google использует стандартный OIDC handler, code + PKCE, state и nonce. Аккаунты не объединяются автоматически по email.
- Refresh-токены вращаются; в БД находятся их хеши. Браузерный refresh — HttpOnly/Secure cookie, Telegram refresh — в памяти.
- Reset и confirmation используют разные хешированные одноразовые токены. Сброс пароля отзывает существующие сессии.
- Скрытый /login/password — интерфейсный маршрут, не проверка владельца и не роль администратора.

## Секреты и исходники

Bot token, Google Client Secret, Resend API key, JWT signing key и пароль БД хранятся в User Secrets для разработки либо в секретах хостинга. Обфускация не делает секрет безопасным для публикации.

Не включайте в Git и Docker build context:

- заполненные env-файлы, secrets.json и локальные конфигурации;
- дампы БД, ключи TLS и закрытые ключи;
- коды восстановления и финансовые экспорты, включая ciphertext-копии;
- traces, скриншоты и логи с пользовательскими данными.

.gitignore и .dockerignore исключают основные локальные артефакты. Примеры конфигурации содержат только пустые значения/заглушки. finance_dev и синтетические CI-ключи предназначены для локальных или временных окружений.

User Secrets не шифруются и не заменяют защиту доступа к компьютеру.

## Проверка перед коммитом

Включите hook только для текущего клона:

~~~powershell
git config --local core.hooksPath scripts/git-hooks
~~~

Нужен Gitleaks в PATH либо локальный artifacts/security/gitleaks/gitleaks.exe. Hook не устанавливается автоматически при clone. Он проверяет staged diff, в том числе при коммите из GitHub Desktop.

Полная полученная история проверяется отдельно:

~~~powershell
gitleaks git . --log-opts="--all" --redact=100 --no-banner
~~~

CI скачивает фиксированную версию Gitleaks с проверкой SHA256 и сканирует полученные refs. Результат относится к конкретному запуску, а не гарантирует отсутствие всех секретов. CI выполняется после push; локальный hook уменьшает риск первой публикации.

.gitleaks.toml расширяет стандартные правила для FT1, Resend и Neon. Исключения должны быть точными; тестовые каталоги целиком не исключаются.

Проверки зависимостей выполняются отдельно:

~~~powershell
dotnet list package --vulnerable --include-transitive
cd frontend
npm audit
~~~

Недоступность реестра не является успешной проверкой уязвимостей. Обновление зависимостей требует последующих тестов.

## HTTP и нагрузка

Публичный origin использует HTTPS. Secure refresh cookie остаётся включённой за Render/nginx. API не доверяет произвольному X-Forwarded-For или непроверенному JWT для определения лимита.

Общий бюджет — 600 API-запросов в минуту на процесс, до 8 одновременных запросов без очереди. Регистрации, входы и почтовые действия имеют отдельные лимиты. При превышении возвращаются 429 и Retry-After. Таблица настроек: [конфигурация](configuration.md).

Обычное тело запроса ограничено 65 536 байт; auth — 16 384, приватное хранилище — 2 800 000. CSV legacy endpoint имеет отдельное ограничение 4 500 000 байт. Приватный CSV разбирается на устройстве.

Rate limit одного процесса не заменяет сетевую DDoS-защиту хостинга, контроль квот и мониторинг. За прокси несколько пользователей могут делить адрес и квоту.

## Логи и диагностика

Не логируются пароль, financial key, PIN, полный initData, cookies, тела ciphertext и содержимое CSV. При обращении за помощью достаточно времени, маршрута, статуса и trace id. Не пересылайте необработанные логи, email-ссылки или снимки разблокированной финансовой истории.

Наличие секретов в URL стороннего Bot API требует скрывать HTTP-ошибки, содержащие полный адрес. Скрипт configure-telegram.ps1 показывает безопасное сообщение вместо исходного исключения.

## Резервные копии

Дамп содержит персональные и служебные данные, а до переноса может содержать открытые финансы. Ограничьте доступ, шифруйте хранилище копий, задайте срок хранения и проверяйте восстановление в отдельную БД.

Серверный backup сохраняет ciphertext, но не пользовательский финансовый ключ. Одного дампа недостаточно для расшифровки без кода/устройства. Операционные команды: [размещение и обслуживание](deployment.md).

## При утечке

1. Отозвать или сменить секрет у соответствующего провайдера.
2. Обновить его в секретах окружения; при необходимости отозвать сессии.
3. Удалить значение из рабочих файлов и оценить доступ к данным.
4. Проверить Git-историю, артефакты и логи. Новый коммит не стирает старую утечку.
5. Планировать очистку истории и обновление клонов отдельно от обычного релиза.

Не сохраняйте утёкшее значение в описании исправления или отчёте.
