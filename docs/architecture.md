# Архитектура

Finance Tracker состоит из React-клиента и слоистого ASP.NET Core монолита с PostgreSQL. Telegram Mini App открывает тот же клиент, что и браузер. Различается способ аутентификации, а не отдельная финансовая система.

## Компоненты

| Компонент | Ответственность |
|---|---|
| Finance.Api | HTTP endpoints, middleware, JWT/cookies, rate limit, DI, health |
| Finance.Application | Серверные use cases, DTO, валидация и специализированные интерфейсы хранения |
| Finance.Domain | Серверные сущности, значения и бизнес-инварианты без зависимостей от EF/ASP.NET |
| Finance.Infrastructure | EF Core, PostgreSQL, миграции, провайдеры токенов, проверка Telegram и почтовый адаптер |
| frontend/src/features/privateFinance | Клиентский ledger, шифрование, синхронизация, PIN и копии |
| frontend/src/features | Экраны авторизации, категорий, истории, счетов, обзора, бюджетов и импорта |

Application зависит от Domain; Infrastructure реализует интерфейсы Application. API связывает реализации через DI. Generic Repository, MediatR, брокеры и отдельные микросервисы не используются.

## Два потока данных

### Аутентификация и служебные запросы

~~~text
React / Telegram SDK
  → API controller и authentication middleware
  → Application handler
  → специализированный store / адаптер
  → PostgreSQL / внешний провайдер
~~~

Сервер управляет аккаунтами, привязками, сессиями, почтовыми токенами, курсами и зашифрованными envelope. Авторизованный запрос использует проверенный user id из JWT. Backend не доверяет присланным id владельца.

### Финансы приватного аккаунта

~~~text
Форма / фильтр
  → financeHttp
  → session + клиентский ledger
  → проверенный финансовый документ в памяти
  → AES-256-GCM
  → PUT /api/private-finance
  → PrivateFinanceHandler
  → store и PostgreSQL
~~~

financeHttp имеет привычный интерфейс get/post/put для финансовых компонентов, но не отправляет открытые операции на серверные /transactions или /dashboard. Чтение получает актуальный envelope и рассчитывает представление локально. Изменение работает с копией документа, проверяет инварианты, шифрует и сохраняет ревизию.

Сервер не может проверить категории и денежные итоги внутри ciphertext. Его инварианты: владелец, формат и размер envelope, стадия переноса, expectedRevision и mutationId. За валидность расшифрованной модели отвечает клиентский parser/ledger. Legacy API отдельно сохраняет серверные Domain-проверки и ограничения БД.

## Сессии

Telegram initData проверяется HMAC и сроком, после чего используется серверная привязка. Регистрация и повторный запуск не создают несколько аккаунтов для одного Telegram id. JWT Telegram содержит версию привязки; отключение отзывает этот доступ.

Google использует серверный OIDC Authorization Code + PKCE со state/nonce. Идентичность определяется sub, а не совпадением email. Существующий аккаунт подключает Google через авторизованное короткоживущее намерение.

Access token хранится в памяти клиента. Браузерный refresh — в HttpOnly cookie; Telegram refresh — в памяти и отдельном транспортном API. Refresh-токены хранятся в БД хешированными и вращаются при продлении.

При проверке access JWT сервер сверяет security stamp пользователя, а для Telegram — ещё и действующую версию привязки. Сброс пароля меняет stamp и отзывает прежние сессии. В PostgreSQL порядок блокировок user → session согласован с ротацией токенов.

## Финансовые правила

Клиентский документ хранит суммы как десятичные строки; арифметика использует BigInt-копейки. Серверный legacy-код использует decimal и numeric(18,2). Number применяется только для геометрии диаграммы и визуального прогресса.

Балансы, бюджеты, итоги периода и диаграммы выводятся из одних записей. Отдельного изменяемого счётчика расходов нет. Переводы не входят в доходы/расходы; отмена перевода меняет его влияние на остатки.

Календарные даты не преобразуются в локальный часовой пояс браузера. Бизнес-день и границы периодов используют Europe/Moscow; createdAtUtc и остальные технические времена используют UTC.

Быстрый ввод получает категорию из нажатой плашки, запрашивает название и сумму и назначает дату. История отвечает за просмотр и исправление. Изменения инвалидируют соответствующие TanStack Query-представления.

## Конкуренция и повторы

| Механизм | Что защищает |
|---|---|
| version у финансовой записи | Изменение или удаление по устаревшим данным |
| requestId операции | Двойное сохранение одной попытки |
| Хеш нормализованного CSV | Повторное применение того же файла |
| expectedRevision хранилища | Перезапись изменений другого устройства |
| mutationId envelope | Повтор последней записи после потери ответа |

Это разные задачи. Один requestId с другим содержимым даёт конфликт. Удалённая операция имеет отметку запроса и не появляется снова от повтора. Другие файлы с похожими операциями не дедуплицируются автоматически.

Клиентские изменения сериализуются в очереди текущей сессии. При неизвестном результате записи неподтверждённый ciphertext сохраняется на время жизни вкладки; доступны повтор, копия и явный возврат к серверной версии. Автоматического слияния двух историй нет.

## Перенос legacy-истории

До активации приватного режима старые финансы могут находиться в обычных таблицах PostgreSQL.

1. Согласованный экспорт и fingerprint.
2. Шифрование на клиенте и stage.
3. Повторное чтение и расшифровка сохранённой копии.
4. Activate: повторная проверка fingerprint и удаление открытых строк в транзакции.

FinancialPrivacyMiddleware блокирует legacy API уже при наличии staged vault. Session advisory locks удерживаются на одном физическом PostgreSQL-соединении, поэтому transaction pooler и Npgsql Multiplexing не подходят. Прерывание не должно оставлять окно для обхода приватного режима.

Старая резервная копия БД не меняется при удалении строк из текущих таблиц. Полная модель: [шифрование](decisions/private-financial-vault.md).

## Внешние адаптеры

- Mailpit — локальная имитация доставки писем.
- Resend — HTTP-доставка confirmation/reset-ссылок, не хранение финансов.
- Telegram — проверка подписанного запуска; polling и webhook для текущего Mini App не нужны.
- Google — OIDC-провайдер входа.
- Курсы ЦБ — данные отображения валют; исходные суммы не пересчитываются в БД.

Секреты внешних адаптеров доступны только backend. Данные приватного финансового документа не отправляются провайдерам входа.

## HTTP, ошибки и размещение

API использует Problem Details и структурированные логи без тела финансовых документов, паролей и токенов. Отмена HTTP передаётся асинхронным серверным операциям.

Render Dockerfile собирает frontend в wwwroot API; локальный и production Compose используют отдельный nginx. Общий origin сохраняет относительные /api URL и cookie-поток без отдельной CORS-схемы. SPA index не кешируется как immutable; assets имеют хешированные имена. Неизвестные API и отсутствующие assets возвращают 404.

Схема меняется EF Core migrations. Тесты отдельно проверяют инварианты клиента, серверные транзакции с PostgreSQL и UI. Подробности: [API](api.md), [конфигурация](configuration.md), [тестирование](testing.md).
