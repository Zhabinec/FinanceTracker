# Архитектура и решения

## Путь запроса

На примере создания расхода:

1. React проверяет форму, отправляет сумму строкой и календарную дату. Axios добавляет JWT из памяти.
2. nginx (либо Vite в разработке) проксирует `/api` в ASP.NET Core.
3. JWT middleware проверяет подпись, issuer, audience и срок действия. Контроллер превращает body в команду и передаёт cancellation token.
4. Handler получает пользователя через `ICurrentUser`, проверяет значения и загружает его категорию. Владелец не берётся из body.
5. Domain проверяет сумму, точность, владельца категории, совпадение типов и активность категории.
6. Infrastructure блокирует строку категории на время новой записи и повторно проверяет активность. Деактивация не может вклиниться между этой проверкой и INSERT. EF Core сохраняет данные; составной FK дополнительно защищает владельца и тип.
7. Handler возвращает DTO, контроллер — HTTP 201. React инвалидирует кеш журнала и dashboard.

При обновлении и удалении клиент передаёт версию операции. Прикладная проверка выявляет уже устаревший экран, а concurrency token в SQL WHERE защищает от изменений между чтением и записью. Если затронуто ноль строк, API возвращает 409. Форма сохраняет версию начала редактирования, даже если фоновый запрос уже загрузил новую запись.

## Почему такие решения

### Счета и баланс

`AccountsController → AccountHandler → IAccountStore → AccountStore → PostgreSQL`.
Domain хранит название, валюту, начальный остаток, архивность и версию счёта.
Валюта и начальный остаток неизменяемы; переименование и архивирование меняют UUID
версии. Application получает владельца из `ICurrentUser`, а валюту — из профиля,
поэтому клиент не может подставить владельца или неподдержанную валюту.

Баланс вычисляется одним SQL-запросом: начальный остаток плюс сумма доходов минус
сумма расходов. Отдельный обновляемый balance не используется: он потребовал бы
синхронизации при каждом изменении операции и мог бы разойтись с историей.
Коррелированная агрегация работает в PostgreSQL по индексу `AccountId, UserId`,
а не загружает все операции в память или отдельным запросом на каждый счёт.

Идентификатор основного счёта совпадает с id владельца. Это явное соглашение для
миграции старой истории и совместимости запросов без `accountId`; это не проверка
прав доступа. Каждый выбор счёта проверяется по `Id` и `UserId`, а составной FK
`transactions(AccountId, UserId) → accounts(Id, UserId)` повторяет ограничение в БД.
Новая регистрация сохраняет пользователя и основной счёт одним SaveChanges.

При назначении счёта новой операции `TransactionStore` берёт `FOR SHARE` и повторяет
проверку архивности перед записью. UPDATE архивности получает несовместимую
блокировку, поэтому гонка не оставляет операцию, назначенную уже архивному счёту.
Исправление исторической операции с тем же архивным счётом разрешено. Изменение
счёта, суммы или типа сразу учитывается в следующем расчёте баланса.

На собеседовании здесь стоит объяснять различие оборота за период и баланса,
защиту владельца на уровне API и FK, optimistic concurrency для формы счёта и
блокировку между проверкой доступности и назначением счёта. Переводы и курсы
добавляются следующими отдельными сценариями, не требуют зависимости Domain
от веб-интерфейса или Telegram.

| Решение | Решаемая проблема | Альтернатива |
|---|---|---|
| Слоистый монолит | Явный поток выполнения, простой запуск небольшого продукта | Микросервисы добавили бы распределённые операции без потребности |
| Прямой DI handlers | Сценарий явно виден в контроллере | MediatR пока не решает необходимую задачу |
| Специализированные stores | Application независим от EF, запросы оптимизированы под сценарий | Generic Repository скрывал бы возможности EF за общим CRUD |
| decimal + строки в HTTP | Копейки сохраняются на всём диапазоне БД | JS number теряет точность; для форм и отображения decimal-библиотека не требуется |
| DateOnly в запросе, UTC в БД | Календарный день отделён от технического момента времени | Timezone браузера менял отображаемый день |
| UUID как версия | Обнаруживает устаревшие изменения и удаления | PostgreSQL xmin также подходит, но привязывает версию к БД |
| Offset pagination, максимум 100 | Номера страниц и ограниченный размер ответа | Keyset лучше для глубокой истории, но усложняет произвольные переходы |
| Repeatable Read для dashboard | Сводка и последние операции видят один снимок | Отдельные Read Committed запросы могут увидеть разные состояния |
| FOR SHARE при назначении категории | Закрывает гонку проверки активности и сохранения | Одной ранней проверки в handler недостаточно |
| Отдельный migration service | Применяет изменения схемы перед стартом API | Миграции в каждом экземпляре API усложняют эксплуатацию |

Агрегации и фильтрация выполняются в БД. Пользовательские фильтры дополняют обязательное условие владельца; поля сортировки разрешены явно. Асинхронные операции получают cancellation token. При отмене браузерного чтения Axios получает AbortSignal.

## Ошибки и логи

Перевод проходит через `TransfersController → TransferHandler → AccountTransfer →
TransferStore`. Один перевод — одна строка `account_transfers` с источником,
получателем, суммой, валютой и идентификатором запроса. Балансы используют
агрегации по этой строке: списание и зачисление видны одним SQL-снимком. Две
отдельные доходные/расходные операции здесь не подходят: они искажали бы отчёты
и требовали бы синхронизации двух записей. Переводы не входят в таблицу transactions.

Составные FK источника и получателя включают UserId. Перед вставкой в транзакции
берутся упорядоченные `FOR SHARE` на оба счёта и повторно проверяются владелец,
архивность и валюта. Уникальный индекс `(UserId, RequestId)` защищает и от
одновременных повторов запроса. При конфликте уникальности вставка откатывается,
контекст отсоединяет несохранённый объект и читает сохранённый результат;
Application сравнивает исходные параметры и отклоняет изменение смысла запроса.

Отмена устанавливает CancelledAtUtc с проверкой Version, а не удаляет строку:
история и ключ идемпотентности сохраняются. Балансы исключают отменённые записи,
поэтому отмена убирает обе стороны перевода одновременно. Отрицательный баланс
допускается существующим правилом счетов. На собеседовании этот срез позволяет
объяснить атомарность, идемпотентность при потере ответа, бизнес-смысл перевода
и защиту владельца в Application и PostgreSQL.

Общая оболочка `AppShell` находится внутри одной защищённой layout-route;
React Router `Outlet` меняет содержимое, сохраняя шапку, навигацию и выход.
Отдельные страницы больше не содержат собственных отличающихся меню.
Один набор NavLink используется и сверху на ПК, и внизу на телефоне: CSS
меняет позицию панели, а не набор пунктов. `aria-current` задаёт активный раздел,
иконка выхода имеет доступное название, есть переход к основному содержимому.

У нижней панели зарезервирован отступ содержимого с safe-area. Оболочка
не содержит финансовых правил или кода Telegram; это позволяет впоследствии
адаптировать внешний chrome под Mini App, сохранив экраны и API. Встраивание
Telegram SDK сейчас не решает задачу адаптивного интерфейса и не добавлено.
Проверки обходят все пять экранов на четырёх ширинах, проверяют порядок
навигации, текущий пункт, позицию при прокрутке и отсутствие переполнения
с раскрытыми формами. Backend этим изменением не затронут.

Быстрый ввод повторно использует существующий маршрут создания операции и
`CreateTransactionHandler`. Модальное окно передаёт выбранную категорию, её
неизменяемый тип, счёт, название в `description` и decimal-сумму строкой.
При отсутствии `occurredOn` Application вычисляет московский день из одного
значения `IClock.UtcNow`; оно же становится `CreatedAtUtc`. Поэтому часы и
часовой пояс браузера не определяют дату быстрого ввода. Сервер повторяет все
проверки владельца, активности и точности суммы. Отдельный endpoint с дубликатом
бизнес-логики не нужен. После сохранения React обновляет кеш операций,
dashboard и счетов. Отмена использует DELETE с возвращённой версией записи;
устаревшая версия не удаляет уже исправленную операцию.

Категория представлена нативной кнопкой, растянутой на всю карточку. Кнопка
настроек и её действия — соседние элементы, а не вложенные кнопки. Это сохраняет
клавиатурное управление и исключает всплытие клика настроек в быстрое добавление.
Декоративное содержимое карточки не перехватывает нажатия; меню закрывается
при Escape, уходе фокуса и нажатии снаружи. Адаптивная сетка проверяется на
320, 390, 768 и 1280 px, включая свободные области карточки и длинные названия.

Переключение валюты — отдельный сценарий представления данных. Защищённый
`CurrenciesController → IExchangeRateProvider → CbrExchangeRateProvider`
получает XML ЦБ, делит значение на номинал и отдаёт decimal-курсы строками.
Один снимок на час разделяется запросами через SemaphoreSlim; отмена запроса
сохраняется, сетевые и XML-ошибки становятся 503. XML запрещает DTD и внешние
сущности, размер ответа и время загрузки ограничены. Одна минута задержки
после сбоя защищает внешний источник от повторных запросов каждого клиента.

React использует общий CurrencyDisplayProvider: исходная сумма × рублей за
единицу исходной валюты ÷ рублей за единицу выбранной. Для представления
decimal-строки переводятся в целочисленные дроби BigInt; округляется только
конечная сумма до двух знаков, половины от нуля. JS number для денег и курсов
не применяется. Форма редактирования получает исходное значение API, а не
пересчитанное представление. Ошибка или ожидание курса сохраняет исходную
валюту подписи. Изменение базовой валюты в БД здесь было бы ошибкой: оно
изменило бы смысл старой истории без реальной конвертации.

400 — неверные значения; 401 — нет действующей авторизации; 404 — ресурс не найден среди доступных пользователю; 409 — конфликт имени, категории или версии.

Неожиданные исключения логируются сервером. Клиент получает безопасный Problem Details с traceId, без stack trace и внутреннего сообщения. Лог запроса содержит метод, путь, статус, длительность и traceId. Тела запросов, пароли и токены не логируются. Используется встроенное логирование ASP.NET Core без новой production-зависимости.

## Тесты

- Domain/Application: бизнес-правила, валидация, владение, расчёт результата, московские даты.
- PostgreSQL integration: миграции, HTTP auth/cookies, precision, фильтры и страницы, агрегаты, изоляция, конкурентные изменения, ротация токенов, ошибки, гонка деактивации.
- Frontend unit: точное форматирование денег и независимость календарной даты от timezone.
- Chromium E2E: путь от регистрации до расхода, dashboard, удаления и выхода; восстановление сессии после reload.

Тест с заглушкой store не доказывает правильность SQL. Для этого нужна PostgreSQL. Браузерный сценарий проверяет совместную работу реальной сборки frontend, nginx, API и БД.

## Для последующего разбора

Стоит уметь объяснить: почему проверки есть в Application/Domain и БД; чем аутентификация отличается от проверки владельца; почему FK не заменяет авторизацию; где проходит транзакция; почему предварительной проверки версии мало без SQL concurrency token; почему результат периода не равен остатку счёта; зачем периоду бизнес-часовой пояс; чем integration-тест отличается от unit-теста.

Исходный MVP не включал счета, импорт, бюджетирование и валюты. Их расширение согласовано в разделе 17 PROJECT.md. Восстановление пароля теперь реализовано: хешированный одноразовый токен, ограниченный срок, rate limit, почтовый адаптер и смена security stamp для отзыва всех сессий. Проверка stamp требует чтения пользователя при авторизованном запросе; это осознанный компромисс для немедленного отзыва JWT.

Application зависит от IRecoveryEmailSender и IConfirmationEmailSender. Infrastructure реализует доставку через HTTP API Mailpit или Resend. Domain не знает о способе доставки и не зависит от SDK провайдера. Подтверждение email реализовано отдельным типом хешированного одноразового токена: reset-токен не подходит для подтверждения и наоборот. GET ссылки не расходует токен; явный POST подтверждает адрес под блокировкой строки, а вход и refresh проверяют подтверждённость. При недоступной доставке можно запросить новое письмо для уже созданного аккаунта.

Ротация refresh-токена использует Read Committed и блокировки строк вместо
конкурирующих Serializable-транзакций. Сначала берётся `FOR SHARE` на пользователя,
затем `FOR UPDATE` на текущую сессию. Повторный запрос после ожидания видит отзыв
токена и получает 401. Порядок «пользователь → сессии» согласован со сбросом
пароля: смена security stamp не пересекается с выпуском новой действующей сессии.
Интеграционные тесты проверяют одновременное использование одного токена и
гонку ротации со сбросом пароля.

Клиент не держит reset-токен в состоянии, инициализированном только при первом открытии формы: источник — текущий fragment маршрута. При смене ссылки форма получает новое состояние. Пароль не модифицируется paste-обработчиком; глобальная защита касается только повторных keydown при удержании shortcut. Регрессии используют настоящий clipboard и клавиатурные команды, а не только Playwright fill(). Публичное развёртывание пока не заявлено как выполненное.
## Месячные бюджеты и CSV-импорт

Бюджеты: React → BudgetsController → BudgetHandler → MonthlyBudget / IBudgetStore
→ EF Core → PostgreSQL. Domain проверяет владельца, расходный тип, первое число
месяца и decimal-лимит; Application проверяет текущего пользователя и version.
В БД составной FK `(CategoryId, UserId, Type)` и CHECK расходного типа не дают
назначить чужую или доходную категорию даже в обход HTTP. Уникальный индекс
`(UserId, Month, CategoryId)` защищает два параллельных создания. Guid Version —
optimistic concurrency token для изменения/удаления; устаревшее действие даёт 409.
Лимит для неактивной категории разрешён: архивирование не удаляет историю.

Лимит хранится, расход рассчитывается SQL-подзапросом в одном запросе на месяц.
Отдельный изменяемый счётчик не нужен: редактирование, удаление и импорт автоматически
меняют результат. Границы месяца переводятся из Москвы в UTC, конец исключён;
учитываются все записанные даты месяца, переводы в выборку не входят. Remaining
неотрицателен, превышение передаётся отдельно. Decimal-суммы в HTTP — строки,
приблизительное число используется только для визуальной полосы progress.

Импорт: выбор локального файла → сопоставление колонок → POST preview → ImportHandler
→ ограниченный CsvReader → проверка всех строк через собственные категории/счёт.
Предпросмотр не меняет БД. POST apply проходит тот же код повторно и создаёт
обычные Domain Transaction. ImportStore в одной транзакции блокирует категории
и счёт FOR SHARE, проверяет актуальное состояние, сохраняет операции и ImportBatch.
Если архивирование/деактивация опередили применение, импорт целиком отклоняется.
Отмена HTTP передаётся до EF Core; оригинальные строки файла в БД не сохраняются.

SHA256 нормализованного содержимого хранится с UserId в уникальном индексе.
Это защищает и повтор после потери ответа, и параллельные apply. Изменение имени
файла/счёта/колонок не разрешает повтор того же файла. Другой файл с теми же
отдельными операциями требует проверки пользователем; без внешних ID нельзя
безошибочно отличить повтор от двух одинаковых покупок. Поэтому автоматическое
удаление похожих записей не вводилось. Также не добавлялись постоянные staging-
таблицы и фоновые очереди: для ограниченных 1000 записей достаточно синхронного
предпросмотра и атомарного применения. Новых production-зависимостей нет.

Frontend обновляет запросы истории, счетов, dashboard и бюджетов после успешного
импорта; правки расходов и быстрый ввод также инвалидируют бюджеты. Отдельные
страницы загружаются через React.lazy, Suspense сохраняет навигацию на месте.
Общие финансовые сценарии доступны через Application и HTTP без привязки к React
или Telegram; будущий клиент сможет использовать те же правила.

### История и ввод

Раздел /transactions называется «История» и отвечает за чтение, фильтры,
исправление и удаление доходов/расходов. Первое действие на странице — работа
со списком; импорт свёрнут под ним. Создание через отдельную полную форму
удалено по запросу разработчика как дублирование быстрого ввода в категориях.
Дата остаётся полем редактирования записи; формат серверного API не меняется.
Удалены только frontend-форма и её mutation: категории продолжают вызывать
POST /api/transactions, а история — GET, PUT и DELETE с прежними проверками
владельца, версии и инвалидацией итогов/бюджетов. Навигационная подпись и title
меняются, URL сохраняется для существующих ссылок и фильтра счёта.

Референсы: [Wallet: фильтры истории](https://support.budgetbakers.com/hc/en-us/articles/7076754432146-Working-with-Filters)
и [Actual Budget: журнал счёта](https://www.actualbudget.com/docs/tour/accounts/).
Используется общий принцип списка записей с фильтрами. Оба продукта допускают
дополнительные действия; решение убрать дублирующий ввод — требование нашего
продукта, а не утверждение, что эти приложения устроены точно так же.
